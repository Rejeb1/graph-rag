MCP follows a client-server architecture built around three kinds of participants: the MCP host, the MCP client, and the MCP server. Understanding how these three relate to each other is the key to understanding the rest of the protocol.

The MCP host is the AI application itself, the program a person actually interacts with. Claude Desktop, Claude Code, and code editors such as Visual Studio Code are all examples of MCP hosts. A host's job is to coordinate the overall user experience and to manage however many MCP connections that experience requires. A host rarely talks to a server directly; instead, for every MCP server it wants to connect to, the host creates a dedicated MCP client. Each client maintains exactly one connection to exactly one server. If a host is connected to three different servers, it will have instantiated three separate client objects internally, each responsible for one of those connections.

The MCP server is the program that actually provides context or capabilities: it might expose a company's Sentry error-tracking data, the contents of a local filesystem, or the schema and query interface of a database. Servers can run in two different places. A local server runs on the same machine as the host, communicating over standard input and output streams; the local filesystem server that ships as a reference implementation is a typical example, and Claude Desktop can launch it as a subprocess. A remote server runs elsewhere, such as on a vendor's own infrastructure, and is reached over the network; the official Sentry MCP server is an example, running on Sentry's own platform rather than the user's machine. This local-versus-remote distinction lines up closely, but not perfectly, with which transport a server uses: local servers typically use the stdio transport and serve a single client at a time, while remote servers typically use the Streamable HTTP transport and are built to serve many clients concurrently.

Underneath these participants, MCP itself is organized into two layers. The data layer is the inner layer, and it defines the actual protocol messages exchanged between a client and a server: how a client discovers what a server supports, what version of the protocol they are speaking, and the core primitives, such as tools, resources, and prompts, that a server can expose. The data layer is built on JSON-RPC 2.0, a lightweight remote procedure call format where every message is either a request expecting a response, or a notification that expects none. The transport layer is the outer layer, and it is responsible for actually moving those JSON-RPC messages between processes, including how a connection is established, how messages are framed on the wire, and how authorization is handled for remote connections. Because the transport layer is a separate concern from the data layer, the same JSON-RPC message format works whether the underlying transport is stdio or Streamable HTTP.

One deliberate design choice in the data layer is that MCP is a stateless protocol at the level of individual requests: every request carries the protocol version and the capabilities relevant to that request in a metadata field, so a server does not need to infer anything about a client from earlier requests in the conversation. Clients typically also identify themselves in this same metadata. Before making other requests, a client can optionally send a server/discover request, which every compliant server must implement, and which returns the server's supported protocol versions, its capabilities such as which primitives it exposes, and identifying information such as its name and version. Because this discovery response can be cached for a period of time indicated by the server, a client does not need to repeat the discovery exchange before every subsequent request.

A concrete example ties these pieces together. When Visual Studio Code, acting as a host, connects to the Sentry MCP server, the Visual Studio Code runtime instantiates a new MCP client object whose only job is to maintain that one connection. If the same Visual Studio Code instance also connects to the local filesystem server, it instantiates a second, independent client object for that connection. The two client objects operate side by side inside the host, each unaware of the other, while the host itself is responsible for combining whatever tools, resources, and prompts both servers expose into a single experience for the person using the editor.
