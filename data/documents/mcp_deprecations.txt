As MCP has evolved, protocol version 2026-07-28 marked several features as deprecated and scheduled for eventual removal. Understanding what changed, and why, is useful both for reading older MCP servers and for understanding the design principles the protocol is converging on.

Three features were deprecated as of this version: roots, sampling, and logging. All three shared a common theme: each one asked the MCP client to take on a responsibility that, in practice, was better handled either by the server itself, by direct configuration, or by an external, purpose-built system.

Roots, the mechanism by which a client communicated which filesystem directories a server should focus on, were deprecated because they only ever functioned as an advisory coordination signal rather than an enforced boundary. A server was expected to respect the root directories a client provided, but nothing in the protocol required it to, and real filesystem security still had to come from operating-system-level permissions or sandboxing regardless of whether roots were used. Given that roots added protocol complexity without adding real security guarantees, the recommended replacement is simpler: pass whatever directory or file information a server actually needs directly, through tool parameters, through resource URIs, or through the server's own configuration, rather than through a dedicated roots mechanism.

Sampling, the mechanism by which a server could ask a client to run a language model completion on its behalf, was deprecated in favor of servers integrating directly with a large language model provider's own API. The original motivation for sampling was to let a server perform AI-dependent reasoning without needing its own model access or its own billing relationship with a model provider, while keeping the client in control of permissions and cost through human-in-the-loop approval of both the request and the response. In practice, direct provider integration turned out to be the more robust path: it avoids routing every AI-dependent operation through a multi round-trip approval flow, and it lets a server choose and control its own model behavior rather than depending on whatever the connected client happens to support.

Logging, which allowed a server to send log messages to a client for debugging and monitoring, was deprecated in favor of two more conventional approaches: for servers using the stdio transport, writing log output directly to standard error, which is already a well-understood channel separate from the protocol messages on standard output and standard input; and more generally, using OpenTelemetry, an existing, purpose-built observability standard, rather than piping logs through MCP itself. This mirrors the same underlying principle as the other two deprecations: MCP is meant to define how AI applications exchange context and capabilities, not to reinvent solutions to problems, like observability, that already have mature, dedicated tooling.

None of these three deprecated features were removed outright in protocol version 2026-07-28; they are marked deprecated and scheduled for removal in a future version, which gives existing servers and clients time to migrate. New implementations, however, are explicitly discouraged from building on roots, sampling, or logging, and are instead pointed toward the simpler, more directly-integrated alternatives described above: explicit parameters and configuration instead of roots, direct provider API calls instead of sampling, and standard error or OpenTelemetry instead of protocol-level logging.

Taken together, these deprecations reflect a broader shift in MCP's design philosophy toward keeping the protocol focused specifically on the exchange of context and capabilities between a client and a server, and away from features that ask the protocol to also mediate concerns, like filesystem security, model access, or observability, that are already well served by other layers of the system.
