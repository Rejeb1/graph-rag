The transport layer is the outer of MCP's two layers, and its job is to move JSON-RPC 2.0 messages between an MCP client and an MCP server: establishing the connection, framing individual messages on the wire, and, for network connections, handling authorization. Because the transport layer is kept separate from the data layer that defines what the messages mean, the same JSON-RPC message format is used no matter which transport carries it. MCP currently defines two transport mechanisms: the stdio transport and the Streamable HTTP transport.

The stdio transport uses a local process's standard input and standard output streams to carry messages directly between two processes running on the same machine. There is no network involved at all: the host launches the server as a subprocess, writes JSON-RPC requests to its standard input, and reads JSON-RPC responses and notifications from its standard output. Because the two processes are talking over an in-memory pipe rather than a network socket, this transport has essentially no communication overhead, which makes it well suited to local servers such as the reference filesystem server, which Claude Desktop can launch directly as a subprocess. Servers using stdio are described as local servers, and because a subprocess's standard streams are naturally a private, one-to-one channel, a stdio server typically serves exactly one client for its entire lifetime.

The Streamable HTTP transport is designed for the opposite situation: a server that runs somewhere other than the user's own machine and needs to be reachable over a network, potentially by many clients at once. Streamable HTTP uses ordinary HTTP POST requests to carry messages from client to server, with the option of Server-Sent Events layered on top so that a server can stream a response back incrementally rather than only returning a single complete payload. Because it is built on standard HTTP, this transport also supports standard HTTP authentication mechanisms out of the box, including bearer tokens, API keys, and custom headers, and MCP specifically recommends using OAuth to obtain the authentication tokens used to secure these connections. The official Sentry MCP server, which runs on Sentry's own infrastructure rather than the user's machine, is a representative example of a Streamable HTTP server: it is described as a remote server, and because HTTP connections are cheap to open and close relative to a long-lived local subprocess, a Streamable HTTP server is typically built to serve many clients concurrently rather than being dedicated to one.

The choice between local, stdio-based servers and remote, HTTP-based servers is not purely technical; it reflects two different deployment stories. A stdio server ships as a program the end user's machine runs directly, which means the user, or the host application on their behalf, is responsible for installing and updating it, but in exchange the server can access local resources, such as the filesystem, directly and with minimal latency. A Streamable HTTP server ships as a hosted service that a vendor operates and updates centrally, which means users get a maintained integration without installing anything, but the server can only see whatever the client sends it over the network rather than anything on the user's own machine. Server authors choose between the two transports based on where the data or capability they want to expose actually lives, and whether they want end users to run something locally at all.

Because the transport layer only concerns itself with moving bytes and authorizing connections, everything described elsewhere in MCP, the participant model of hosts, clients, and servers, the request and notification semantics of JSON-RPC, and the tools, resources, and prompts primitives, works identically regardless of which transport is in use. A developer building against the MCP SDKs generally writes their server or client logic once against the data layer, then chooses stdio or Streamable HTTP, or in principle supports both, purely as a deployment decision.
