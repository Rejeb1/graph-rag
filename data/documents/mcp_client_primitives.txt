Just as MCP servers can expose primitives to clients, MCP defines primitives that flow in the other direction: capabilities a client can offer back to a server, so that server authors can build richer, more interactive experiences. The main client-side primitive still in active use is elicitation; two others, roots and sampling, have been deprecated as of protocol version 2026-07-28 and are scheduled for removal, though understanding them still helps explain why elicitation is shaped the way it is.

Elicitation lets a server request specific information from a user in the middle of handling a request, rather than requiring all necessary information to be supplied up front or simply failing when something is missing. This makes interactions more flexible: a server can start working with what it has and pause to ask for exactly what it is still missing. Elicitation supports two modes. Form mode is used when the server wants the client to collect structured data through a schema-driven form; the server supplies a JSON Schema describing the fields it needs, such as a boolean confirmation flag or an enumerated seat preference, and the client builds an input form from that schema and validates the user's response against it before returning it. URL mode is used instead when the interaction is sensitive, for example a third-party OAuth authorization or entering payment details; in this mode the server gives the client a URL to show the user, the client asks for explicit consent before opening it, and the actual data exchange happens directly between the user and that external site rather than passing through the client or ever entering the server's or the language model's context. Because of this privacy boundary, servers must never use form mode to request passwords, API keys, access tokens, or payment credentials; those cases always belong in URL mode.

Mechanically, elicitation is delivered through what MCP calls the Multi Round-Trip Requests pattern. When a server is handling a request, such as a tools/call invocation, and realizes it needs more information, it responds not with a final result but with an InputRequiredResult containing one or more elicitation/create requests. The client gathers the requested input from the user, then retries the original request, attaching the collected responses. A travel-booking example illustrates this well: a server finalizing a Barcelona vacation booking might elicit confirmation of the trip details, a seat preference, a room type, and whether to add travel insurance, all through a single form-mode request, before completing the booking.

Roots are a now-deprecated mechanism by which a client tells a server which filesystem directories it should focus on, communicated as one or more file:// URIs. A travel-planning workspace might expose separate roots for a main planning directory, a directory of reusable itinerary templates, and a directory of client travel documents, letting a well-behaved server know where to read and write without being told the exact rules for every operation. It is important to understand what roots are not: they are a coordination mechanism, not a security boundary. The specification only ever said servers should respect root boundaries, not that they must enforce them, because a server runs code the client does not control; actual security has to be enforced at the operating system level, through real file permissions or sandboxing. Roots work well when a server is already trusted, and the goal is preventing accidental scope creep rather than stopping deliberately malicious behavior. New implementations are expected to pass directory or file information through tool parameters, resource URIs, or server configuration instead of through roots.

Sampling let a server ask the client to run a language model completion on its behalf, so that the server could perform AI-dependent reasoning without integrating with or paying for a model provider directly. Because the client already has model access on behalf of the user, sampling put the client in control of permissions and safety, and the flow was designed around human-in-the-loop review: a server would send a sampling/createMessage request describing the messages, model preferences, and constraints for the completion it wanted, and the client would let the user review and approve both the outgoing request and the model's response before the flow continued. A flight-booking tool that had gathered dozens of raw flight options might use sampling to ask an LLM to weigh price against convenience and recommend the best one, given the user's stated preferences. New implementations are now expected to integrate directly with an LLM provider's own API instead of routing that reasoning through the client via sampling.
