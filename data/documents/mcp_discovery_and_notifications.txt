Before an MCP client and server can do anything useful together, they need a way to agree on what each of them supports. MCP handles this through a discovery exchange and, once a connection is established, an opt-in notification system that keeps both sides synchronized as things change.

Every MCP request, not just the discovery request itself, carries a metadata field containing the protocol version the sender is speaking and the capabilities relevant to that request; clients typically also identify themselves by name and version in this same field. This design is what allows MCP to remain a stateless protocol at the request level: because every request already carries this context, a server never has to infer a client's version or capabilities from earlier messages in the conversation.

Formal discovery happens through a server/discover request, which every compliant MCP server is required to implement, though sending it is optional for a client. A client that wants to know what a server supports before issuing any other request sends server/discover and receives back a result describing three things: which protocol versions the server supports, which capabilities it has, such as whether it exposes tools, resources, or prompts and whether it supports change notifications for each, and identifying information about the server itself, such as its name and version. If a client requests a protocol version the server does not support, the server rejects the request and lists the versions it does accept, and the client is expected to retry with one of those. Because the discovery response includes a time-to-live hint indicating how long it can safely be cached, a client does not need to repeat this exchange before every subsequent request; it can reuse what it already learned until that cache window expires.

Tool discovery follows a similar but more specific pattern using tools/list, which a client sends to learn exactly which tools a server currently offers, complete with each tool's name, description, and input schema, before attempting to call any of them. Like the discovery response, a tools/list response can carry its own cache hint, and it supports pagination through an optional cursor parameter for servers with large tool sets.

Because a server's state can change after a connection is already established, for instance because a new tool becomes available, an existing one is modified, or one becomes temporarily unavailable, MCP layers a notification system on top of this discovery model rather than requiring clients to continually re-poll. Notifications are opt-in on both sides. A server must first declare, as part of its discovered capabilities, that it supports change notifications for a given primitive, for example by including a listChanged flag under its tools capability. A client that wants to receive these notifications then opens a long-lived subscription by sending a subscriptions/listen request naming the specific notification types it wants, such as tool list changes. The server acknowledges the subscription, and its acknowledgment reflects only the subset of the requested notification types it is actually willing to honor, silently omitting any it does not support.

Once a subscription is open, notifications arrive as ordinary JSON-RPC notification messages, meaning they carry no id field and expect no reply, consistent with JSON-RPC 2.0's notification semantics generally. Each notification delivered on a subscription carries the identifier of the subscriptions/listen request that opened it, so a client managing several subscriptions at once can tell which one produced a given event. When, for example, a server's tool list changes, it sends a notifications/tools/list_changed message on the relevant subscription; the client's typical response is to immediately re-issue a tools/list request to refresh its view of what the server currently offers, rather than assuming the notification itself carries the updated list.

MCP explicitly documents this notification delivery as best effort rather than guaranteed, particularly across transport reconnects, so clients are expected to also fall back on ordinary polling to keep their view of a server's capabilities fresh over time, rather than relying on notifications as the sole source of truth. The overall effect of combining a cacheable discovery step, an explicit tools/list request, and an opt-in notification stream is that an MCP connection behaves less like loading a fixed manifest once and more like maintaining a live, if imperfect, view of a server's evolving capabilities.
