The most important concept in MCP's data layer is the set of primitives: the specific kinds of context and capability that a server can offer a client, and that a client can in turn offer back to a server. On the server side, MCP defines three core primitives: tools, resources, and prompts.

Tools are executable functions that an AI application can invoke to perform an action, such as making an API call, running a database query, or performing a file operation. A tool is not just a name; each tool a server exposes carries a unique name used to identify it within that server's namespace, a human-readable title meant for display to a user, a description explaining what the tool does and when it should be used, and an input schema, expressed as JSON Schema, that defines what arguments the tool accepts and lets a client validate those arguments before sending them. A calculator tool, for example, might be named calculator_arithmetic, take a single expression argument such as "2 + 3 * 4" or "sqrt(16)", and return the numeric result. A weather tool might be named weather_current, take a location argument and an optional units argument constrained to metric, imperial, or kelvin, and return a description of current conditions at that location.

Resources are data sources that provide contextual information to an AI application, such as the contents of a file, a database record, or the response of an API call. Where a tool represents an action to be taken, a resource represents information to be read. A server exposing context about a database might provide a resource containing that database's schema, letting a client or the AI application behind it understand the shape of the data before writing queries against it.

Prompts are reusable templates that help structure an interaction with a language model, such as a system prompt or a set of few-shot examples tailored to a particular task. Continuing the same database example, a server might pair its query tool and schema resource with a prompt containing few-shot examples of well-formed queries against that schema, giving the AI application a head start on using the other two primitives correctly.

Each of these three primitive types follows the same basic interaction pattern. A client first calls a list method, such as tools/list, resources/list, or prompts/list, to discover what the server currently offers; because this listing is a live request rather than a fixed manifest, what a server exposes can change over time. Tools additionally support a call method, tools/call, used to actually invoke a specific tool with a set of arguments once it has been discovered.

A worked example shows tool discovery and execution end to end. A client sends a tools/list request; the server responds with an array of tool definitions, in this case a calculator tool and a weather tool, each with its name, title, description, and input schema as described above. Having discovered the weather_current tool, the client can then send a tools/call request naming that exact tool and supplying arguments, for instance a location of "San Francisco" and units of "imperial". The server executes the tool and returns a result containing a content array; in this example the content is a single text block describing the current weather in San Francisco. This content array is deliberately generic: MCP supports multiple content types beyond plain text, such as images or embedded resources, so a tool's result can carry richer content than a string when that is useful.

Because a server's available tools can change while a client is connected, for example because a new capability comes online or an existing one is temporarily disabled, MCP also defines a notification system layered on top of these primitives. A server that supports change notifications advertises this in its declared capabilities, and a client that wants to stay current opts in by opening a subscription for the relevant notification type. When the server's tool list subsequently changes, it pushes a notification on that subscription rather than waiting for the client to poll, and the client typically responds by re-issuing a tools/list request to refresh its view. This pattern of listing, invoking, and subscribing to changes is what makes MCP's primitives dynamic rather than a fixed, load-once manifest.
